# ADP AI Agent 运维能力 ToDo 清单

> 状态：规划
>
> 本文将 ADP 从“受控 Tool-Calling 运维 Agent”进一步升级为 AI Agent 运维控制面的工作拆分为可验收任务。
>
> 设计边界：LLM 是不可信决策组件；ADP Server 是可信控制面；Worker 是受限执行面。任何模型工具调用均须经过服务端 Schema、RBAC、策略、风险和审批校验。首版仍聚焦 MySQL 备份、Nginx 可用性诊断、Redis 性能诊断，禁止引入任意 Shell 执行能力。

## 总体原则与分期

| 阶段 | 建议周期 | 交付主题 | 是否可独立上线 |
| --- | --- | --- | --- |
| 阶段 0 | 第 1–2 周 | 数据模型、版本与验收基线 | 否 |
| 阶段 1 | 第 3–8 周 | 可观测、运行排障、自动止损、工具治理 | 是 |
| 阶段 2 | 第 9–15 周 | 策略审批、评测与灰度发布 | 是 |
| 阶段 3 | 第 16–24 周 | 生产反馈闭环、根因分析、多 Agent 运营 | 是 |

不建议在阶段 1 建设通用的多 Agent 自动编排器、向量数据库或独立 ELK 集群。现有 PostgreSQL、审计日志、Prometheus 指标、Agent Runtime、Policy Engine 和 Scheduler 足以先验证真实需求；只有查询量或保留周期证明 PostgreSQL 不足时，再拆分分析型存储。

## 阶段 0：方案冻结与基础标准

### T0.1 定义 Agent 可观测数据模型

- **任务目标**：建立跨 Agent 运行链路的统一事件模型，完整表达 Agent、模型调用、受控工具、Job、审批及最终结果。
- **实施步骤**：
  1. 定义 `Trace`、`AgentRun`、`Turn`、`ModelCall`、`ToolCall`、`Job`、`Approval`、`Guardrail`、`Handoff`、`Evaluation` 等实体及关系。
  2. 明确每类事件的必填字段：运行 ID、父节点 ID、时间、状态、Agent/工具/模型版本、环境、租户或操作者。
  3. 将现有 `AgentRun`、`AuditLog`、Job 和 Approval 记录映射到该模型；保留 `schema_version` 以支持演进。
  4. 定义内容最小化采集、PII/密钥脱敏和按角色查看原文的规则。
  5. 发布 JSON Schema、Go 类型、事件示例和埋点约定。
- **改动点**：
  - 新增 `internal/domain/model/agent_trace.go`、`agent_event.go`。
  - 扩展 PostgreSQL Schema：Trace、Span/Event、内容脱敏标记、版本字段和索引。
  - 在 `internal/application/agent/runtime.go`、Scheduler、Policy、Approval 的关键节点写入事件。
- **测试集**：
  - 单 Agent：模型调用 → 只读诊断工具 → Job 结果 → 报告。
  - 多轮循环：成功、最大步数耗尽、超时、取消。
  - 审批：`running → waiting_approval → running/rejected`。
  - 工具：成功、网络超时、业务失败、参数校验失败。
  - 敏感数据：手机号、密码、Bearer Token、数据库连接串。
- **验收目标**：
  - 所有样例可还原为一条完整父子调用链，关联正确率不低于 99.9%。
  - 100% 事件通过 Schema 校验；未知字段不影响旧版本读取。
  - 默认查询和告警输出中不存在明文敏感字段。
  - 任意 Run 能关联业务请求、操作者、Agent 配置版本和部署环境。

### T0.2 定义 Agent 配置包与版本血缘

- **任务目标**：将模型、系统提示词、工具集、策略、模块模板、知识/案例来源、评测集和 SLO 固化为一个可发布、可追溯、可回滚的配置包。
- **实施步骤**：
  1. 定义不可变 `AgentPackage` Manifest 及版本规则。
  2. 为 `development`、`staging`、`production` 设置仅指向已发布版本的部署别名。
  3. 在创建 Run 时写入配置包版本和依赖版本快照。
  4. 实现两个配置包的结构化 Diff 与历史版本回滚。
- **改动点**：
  - 新增配置包表、发布记录表与读取 API。
  - 扩展 Agent 配置及 Run 记录，增加 `package_version`。
  - 管理端增加版本详情、依赖关系、Diff 和回滚入口。
- **测试集**：
  - 仅改模型参数、仅改 Prompt、仅改工具版本、仅改策略版本。
  - 引用未发布、已删除或不兼容的工具/模板版本。
  - 发布后回滚，并检查存量 Run 的审计数据不被修改。
- **验收目标**：
  - 任意线上 Run 可在 30 秒内定位完整配置包。
  - Diff 可显示模型、Prompt、工具、策略、模板、评测集和 SLO 的变更。
  - 新请求回滚后 100% 使用指定历史版本；历史 Run 保持原始快照。

## 阶段 1：可观测、止损与工具治理 MVP

### T1.1 打通运行事件采集和查询链路

- **任务目标**：使 Agent 的模型调用、工具调用、策略判定、Worker Job 和审批状态进入统一 Trace，而采集故障不能影响实际运维任务。
- **实施步骤**：
  1. 为 Runtime、Tool Executor、Policy Engine、Scheduler、Worker Stream 增加非阻塞事件发布接口。
  2. 采用批量写入和失败降级；事件存储不可用时记录指标并丢弃可重建的观测事件，绝不阻塞受控执行。
  3. 按运行 ID、Agent、模块、Worker、环境、状态、时间范围提供查询。
  4. 输出 Prometheus 聚合指标：Run 成功率、模型耗时、工具失败率、等待审批时长、Token/成本。
- **改动点**：
  - 新增事件 Repository 和异步写入 Worker。
  - 扩展 `/metrics` 与 `internal/interfaces/http/agent_runs.go`。
  - 为查询建立 `run_id`、`parent_event_id`、`created_at` 等索引。
- **测试集**：
  - 高并发提交 Run。
  - 事件存储短暂不可用。
  - 重复投递、乱序投递、跨协程上下文传播。
  - 大模型输出和大工具结果截断与脱敏。
- **验收目标**：
  - 观测写入失败不改变 Job 或审批状态。
  - 常规运行埋点对 Agent 主流程的 P95 额外延迟低于 20ms。
  - 重复事件不会导致成本、错误数或状态被重复计算。
  - 按 Run ID 查询可获得模型、工具、策略和 Job 的完整时间线。

### T1.2 实现 Agent Run 时间线与受控 Replay

- **任务目标**：让运维人员快速定位“失败在哪一步、用了什么输入、为什么被拒绝、是否可安全复现”。
- **实施步骤**：
  1. 在 UI 提供树形 Trace 和瀑布时间线，展示模型、工具、Job、审批、重试和错误。
  2. 支持按步骤类型、状态、风险级别和耗时筛选，并跳转审计日志。
  3. 增加从历史节点复制输入并在隔离环境重放的能力。
  4. Replay 默认禁止写操作模块和高风险外部工具；仅在显式审批后允许受控验证。
- **改动点**：
  - 新增 Trace 查询 API、Trace Tree UI、Replay API。
  - 扩展 RBAC：原文查看与 Replay 权限分离。
  - 增加 Replay 审计事件和隔离环境配置。
- **测试集**：
  - 正常任务、工具超时、模型格式错误、最大步数耗尽。
  - 等待审批、被拒绝、取消、Worker 离线。
  - 含敏感数据的 Run、无 Replay 权限用户。
  - 原工具版本已下线的历史 Run。
- **验收目标**：
  - 常规 Run 页面打开时间小于 3 秒，至少支持 20 层嵌套节点。
  - 模拟事故可在 5 分钟内定位失败节点、原始错误和关联策略。
  - 未明确批准时，Replay 零写操作、零生产 Worker 调度。
  - 原文查看和 Replay 全部可审计。

### T1.3 建立 Agent 成本、循环与行为异常告警

- **任务目标**：在 Token 成本失控、无效循环、工具重试风暴或质量恶化时快速告警并止损。
- **实施步骤**：
  1. 定义单 Run、单会话、单 Agent、单租户的步骤数、Token、预算和时延阈值。
  2. 检测重复工具调用、相同参数重复失败、无状态进展和最大步骤耗尽。
  3. 建立按版本的成本、时延、工具失败率、人工接管率基线。
  4. 对接告警渠道与自动动作：取消 Run、禁用有故障的只读工具、切换人工处理队列。
- **改动点**：
  - 新增告警规则、预算计数器、基线计算任务和告警事件表。
  - Runtime 支持 `cancelled_by_policy` / `budget_exceeded` 终态。
  - 管理端提供规则配置、静默和告警处置记录。
- **测试集**：
  - 无限工具循环、重复参数循环、Token 暴涨。
  - 单一 MCP/模块持续超时。
  - 某配置版本工具失败率突升。
  - 高并发下同源告警的聚合和静默。
- **验收目标**：
  - 预算超限和循环在 1 分钟内产生告警并停止后续高风险动作。
  - 同一根因 10 分钟内只生成一条聚合告警。
  - 告警携带 Agent、版本、失败节点、影响范围、Trace 链接和建议动作。

### T1.4 建设受控工具与 MCP 注册中心

- **任务目标**：将 Agent 可调用能力统一纳管，防止未注册、越权和不符合参数契约的工具执行。
- **实施步骤**：
  1. 建立工具目录：模块/MCP Server、版本、Owner、输入输出 Schema、依赖、环境、风险等级和幂等性。
  2. 维护 Agent 到工具的最小权限授权关系。
  3. 在 Tool Executor 前执行注册、Schema、RBAC、目标范围和策略校验。
  4. 聚合工具成功率、时延、业务失败、网络失败、重试次数和调用成本。
- **改动点**：
  - 扩展 `internal/module.Registry`，新增 Tool Registry 元数据。
  - 扩展 Policy Engine 与配置文件，增加工具风险和授权规则。
  - 新增工具健康度 API/UI。
- **测试集**：
  - 未注册工具、未授权 Agent、参数不符合 Schema。
  - HTTP 成功但业务失败、网络超时、幂等重试。
  - 相同工具多版本共存和版本下线。
- **验收目标**：
  - 未注册、未授权或 Schema 不合法的调用默认拒绝。
  - 所有高风险工具必须具备 Owner、版本、风险等级和输入 Schema。
  - 工具健康指标可按工具版本、Agent、环境查询。

## 阶段 2：策略审批、评测与发布门禁

### T2.1 完善策略引擎与人工审批恢复

- **任务目标**：将高风险 Agent 动作变为可解释、可审核、可恢复的受控工作流。
- **实施步骤**：
  1. 统一策略输入：Agent、操作者、工具、参数、目标、环境、数据标签与风险。
  2. 支持 `allow`、`deny`、`require_approval`、`redact`、`rate_limit` 决策。
  3. 审批时持久化暂停点、工具参数摘要、策略版本和上下文快照。
  4. 审批完成后重新运行 Schema、授权和策略校验，再从原暂停点恢复。
- **改动点**：
  - 扩展 `internal/domain/policy/engine.go`。
  - 扩展 Approval 表、审批 API/UI 和 Runtime Resume 事件。
  - 新增策略版本和审批决策审计字段。
- **测试集**：
  - 生产写入、外发通知、敏感数据导出。
  - 同意、拒绝、超时、重复审批、撤销审批。
  - 审批等待期间配置包或策略发生变更。
  - 恶意或畸形工具参数。
- **验收目标**：
  - 高风险工具 100% 经策略判定；未批准操作零执行。
  - 审批后从原 Run 恢复，不重放已完成的低风险步骤。
  - 每次决策可追溯策略版本、输入摘要、操作者、结果和时间。

### T2.2 建设评测数据集与实验执行器

- **任务目标**：用可重复的测试集验证 Prompt、模型、工具和策略变更，防止质量和安全回归。
- **实施步骤**：
  1. 定义数据来源：人工构造、线上失败、用户差评、人工接管、告警事故。
  2. 建立版本化数据集并按冒烟、回归、安全、工具轨迹、长尾分类。
  3. 支持确定性代码规则、LLM Judge 和人工标注三类评测器。
  4. 支持异步实验、版本对比、失败样本下钻和 Trace 关联。
- **改动点**：
  - 新增 Dataset、DatasetItem、Experiment、Evaluation 数据表与 API。
  - 新增评测任务队列与评测器插件接口。
  - 管理端增加数据集、实验和得分详情页面。
- **测试集**：
  - 结构化报告/JSON 格式。
  - 工具参数合法性、只读工具选择正确性。
  - Nginx、Redis、MySQL 三个既定场景的典型/故障/长尾输入。
  - 提示注入、越权请求、敏感数据泄漏。
  - 多步骤任务的预期工具轨迹。
- **验收目标**：
  - 每个生产 Agent 至少拥有冒烟、安全、回归三类数据集。
  - 两版本可比较任务成功率、规则得分、Judge 得分、成本和时延。
  - 规则评测可重复；Judge 保存评测 Prompt、模型、版本和理由。
  - 失败样本能跳转对应的完整 Trace。

### T2.3 实现灰度发布、影子流量与发布门禁

- **任务目标**：将 Agent 变更从人工经验发布升级为“离线验证—小流量验证—自动放量/回滚”。
- **实施步骤**：
  1. 定义发布路径：离线评测 → Shadow → 5% 灰度 → 25% 灰度 → 全量。
  2. 为新旧 `AgentPackage` 进行流量分配与结果对比。
  3. 配置门禁：安全评测必须通过；质量不得低于基线；成本、时延和工具失败率不得超过阈值。
  4. 自动暂停放量，并提供一键回滚。
- **改动点**：
  - 新增发布控制器、流量路由配置和版本比较任务。
  - Runtime 根据部署别名选择 AgentPackage。
  - 新增发布审计、放量状态和自动回滚事件。
- **测试集**：
  - 离线质量不达标、成本超阈值、工具失败率升高。
  - 灰度指标短暂波动、持续恶化和数据量不足。
  - 回滚时存在运行中或等待审批的 Run。
- **验收目标**：
  - 未通过离线门禁的版本不能进入生产。
  - 灰度越界后 5 分钟内自动暂停放量。
  - 回滚不破坏历史 Run 的配置和审计关联。
  - 每个生产版本均关联评测报告、放量记录及最终决策。

## 阶段 3：生产反馈闭环与多 Agent 运营

### T3.1 将生产问题沉淀为回归测试集

- **任务目标**：让差评、人工修正和运行事故成为下一次发布前必须通过的可管理资产。
- **实施步骤**：
  1. 从差评、人工接管、策略拦截、告警和失败 Run 生成候选样本。
  2. 脱敏、去重、聚类，并交由领域人员审核。
  3. 标注失败类型、预期结论、允许/禁止的工具轨迹和严重等级。
  4. 将审核通过样本加入指定 Agent 的版本化回归集。
- **改动点**：
  - 新增候选样本池、标注审核页面与 Trace 转 DatasetItem 工具。
  - 新增样本保留、删除和脱敏状态管理。
- **测试集**：
  - 重复失败、敏感内容、恶意输入、人工改写后的正确答案。
  - 同一问题在不同模型或版本上的修复回归。
- **验收目标**：
  - P0/P1 事故可在 1 个工作日内进入候选回归集。
  - 样本保留来源 Trace、脱敏状态、审核记录和适用 Agent。
  - 已修复事故可被后续实验自动发现回归。

### T3.2 提供证据驱动的根因分析与优化建议

- **任务目标**：从“有告警”升级到“知道优先修什么、为何判断、如何验证”。
- **实施步骤**：
  1. 聚类模型拒答、工具异常、检索缺失、循环、权限拒绝、报告不合规等模式。
  2. 关联模型、Prompt、工具、策略、模板、Worker 和部署版本。
  3. 输出含证据和风险的建议，如收紧工具参数、补充案例、调整 Prompt 或修复模块。
  4. 每项建议必须关联可运行的评测集；不得自动修改生产配置。
- **改动点**：
  - 新增失败聚类任务、根因规则库、建议记录与验证状态。
  - UI 增加“证据—建议—实验—发布”联动入口。
- **测试集**：
  - 单根因与多根因事故。
  - 版本变更引发的质量下降。
  - Worker/模型供应商故障与知识/案例缺失。
- **验收目标**：
  - Top 10 高频失败类型可自动归类。
  - 每条建议展示证据 Trace、影响范围、风险和验证方式。
  - 所有生产变更均仍需走阶段 2 发布门禁。

### T3.3 多 Agent 协作效能分析（条件实施）

- **任务目标**：当 ADP 确实存在多个协作 Agent 后，识别无效委派、重复调用与关键路径瓶颈。
- **实施前提**：生产中至少有 3 个具有明确职责边界的 Agent，且每月多 Agent Run 数量足以形成稳定样本；不满足时不启动本任务。
- **实施步骤**：
  1. 在 Trace 模型中记录父子 Agent、Handoff、共享上下文和并行关系。
  2. 计算委派成功率、重复工具调用率、上下文成本、关键路径时延和成本归因。
  3. 标识循环交接、角色重叠、上下文丢失与重复工作。
  4. 输出“合并、拆分、缓存或改为确定性工作流”的建议。
- **改动点**：
  - 扩展 Trace 拓扑字段。
  - 新增协作图、关键路径与成本分摊查询。
- **测试集**：
  - 串行委派、并行诊断、循环委派、上下文丢失、重复调用。
- **验收目标**：
  - 可展示单次 Run 与聚合维度的 Agent 协作图。
  - 能识别循环 Handoff、重复工具调用和最长耗时路径。
  - 成本可归因到 Agent、模型、工具和任务。

## 全阶段通用质量门槛

- 所有新增 API 均须完成租户/用户授权、输入校验、审计、限流和错误处理测试。
- 所有高风险工具路径必须有端到端策略与审批测试；HTTP 200 不等于 Agent 任务成功。
- 生产发布前至少完成：单元测试、契约测试、集成测试、故障注入、回归评测和安全测试。
- Trace 内容默认最小化采集；查看原文、导出和 Replay 必须独立授权并保留审计。
- 每个阶段先选择一个低风险诊断 Agent 试点，达标后再扩展到其他 Agent。
- 当指标查询、事件写入或历史保留已成为 PostgreSQL 的明确瓶颈时，再评估 ClickHouse/日志平台；在此之前不增加额外基础设施。
